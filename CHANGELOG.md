# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Versioning by phase: each phase is built in small `-dev` sub-versions
and closes with a consolidation release. Phase 1 runs from `0.0.1-dev`
and closes at `0.1.0-dev`; Phase 2 starts at `0.1.1-dev` and closes at
`0.2.0-dev`, and so on.

## 0.0.7-dev

Phase 1 in progress: BIP-32 hierarchical deterministic (HD) wallets.

### Added

- `VeChainHDKey.fromMnemonic`, which derives the official VeChain
  account node `m/44'/818'/0'/0` by default, with an optional path and
  passphrase
- `VeChainHDKey.fromSeed`, `fromPrivateKey` and `fromPublicKey`
  (watch-only), as in the official SDK
- `VeChainHDKey.derive` for any valid BIP-32 path, and `deriveChild`
  for normal and hardened children
- `VeChainHDKey` getters for the private key (null when watch-only),
  the compressed public key, the chain code, `depth`, `index`,
  `isWatchOnly`, `address` and `keyPair`
- `VeChainHDKey.vetDerivationPath` and `VeChainHDKey.hardenedOffset`
- `VeChainHDKeyException` for malformed paths, wrong seed or chain code
  lengths, out-of-range indexes, and private key operations on
  watch-only keys
- `compressPublicKey` in the internal `VeChainSecp256k1` class
- 30 unit tests, including the official BIP-32 test vectors 1 and 2
  and the official VeChain addresses and private keys derived from the
  official test mnemonic
- Example: `example/phase1/hdkey_example.dart`

### Changed

- `VeChainKeyPair` compresses its public key with the shared
  `VeChainSecp256k1.compressPublicKey` instead of a private copy of the
  same logic

### Fixed

- Three dartdoc warnings ("unresolved doc reference") caused by the
  range `[1, n - 1]` being read as a doc link; the range is now written
  as code

### Design Decisions

- `derive` accepts any syntactically valid BIP-32 path; the official
  `isDerivationPathValid` allows fewer shapes than the official
  `derive` actually accepts
- `fromMnemonic` takes a validated `VeChainMnemonic` instead of raw
  words
- An index that produces an invalid key (odds of about 1 in 2^127)
  throws instead of silently moving to the next index, which would
  return a different account than the one requested
- Extended keys (`xprv`/`xpub` in Base58) are out of scope for now; the
  tests use the official BIP-32 vectors converted to raw chain codes and
  keys, with their checksums verified
- Getters return copies, and `toString` never shows the private key or
  the chain code, since a public key plus its chain code reveals every
  normal child's public key

### Status

Phase 1 in progress: HD wallets complete and verified against the
official BIP-32 vectors and the official VeChain account addresses.  
Not ready for production use.  
Next: Keystore (`0.0.8-dev`).

## 0.0.6-dev

Phase 1 in progress: BIP-39 mnemonics and seed derivation.

### Added

- `VeChainMnemonic.generate` (12, 15, 18, 21 or 24 words; 12 by
  default), `VeChainMnemonic.fromEntropy` and `VeChainMnemonic.parse`
- `VeChainMnemonic.words`, `phrase` and `entropy`, all returned as
  copies
- `VeChainMnemonic.toSeed`, deriving the 64-byte BIP-39 seed with
  PBKDF2-HMAC-SHA512 (2048 iterations) and an optional passphrase
- The official BIP-39 English wordlist (2048 words), generated by
  `scripts/generate_bip39_wordlist.dart`, which checks the SHA-256 of
  the official file before writing it
- `VeChainMnemonicException` for invalid mnemonics, entropy, word
  counts and passphrases
- 29 unit tests, including the 24 official BIP-39 vectors (entropy,
  mnemonic and seed), the official VeChain test mnemonic, and an
  integrity check of the wordlist against the official SHA-256
- Example: `example/phase1/mnemonic_example.dart`

### Design Decisions

- BIP-39 is implemented in the SDK with pointycastle (SHA-256 and
  PBKDF2-HMAC-SHA512) instead of a third-party package: the mnemonic is
  the master secret of every account, and the implementation is
  verified against all the official vectors
- English wordlist only, as in the official VeChain SDK
- `parse` trims the phrase, accepts any whitespace between words and
  ignores letter case, and uses the same normalized words to validate
  and to derive the seed; the official SDK lowercases only when
  deriving
- The passphrase is optional and empty by default, which gives exactly
  the official VeChain SDK seed; only ASCII passphrases are accepted,
  because BIP-39 requires Unicode NFKD normalization, which the Dart
  core libraries do not provide
- `toString` never shows the words, and errors identify an invalid word
  only by its position

### Status

Phase 1 in progress: BIP-39 mnemonics and seed derivation complete and
verified against all 24 official BIP-39 vectors.   
Not ready for production use.   
Next: HD wallet (`0.0.7-dev`).

## 0.0.5-dev

Phase 1 in progress: secp256k1 signatures and public key recovery.

### Added

- `VeChainKeyPair.sign`, which signs a 32-byte hash and returns a
  `VeChainSignature`
- `VeChainSignature`: a validated 65-byte signature (r + s + recovery)
  with `fromBytes`, `bytes`, `r`, `s`, `recovery`, value equality and a
  hex `toString`
- `VeChainSignature.recoverPublicKey` and
  `VeChainSignature.recoverAddress`, which identify the signer of a hash
- `sign` and `recoverPublicKey` in the internal `VeChainSecp256k1`
  class, with the recovery byte and public key recovery implemented by
  the SDK (SEC 1, section 4.1.6)
- 26 unit tests, including the official signature vector from the
  VeChain SDK for JavaScript and an independent vector with recovery
  byte 1
- Example: `example/phase1/signature_example.dart`

### Design Decisions

- Signatures use RFC 6979 (a deterministic nonce derived with
  HMAC-SHA256), so the same hash and key always give the same
  signature, matching the official SDK byte for byte
- Signatures are always normalized to a low S, because the VeChainThor
  transaction pool rejects high-S signatures (including the gas payer
  signature under VIP-191) to prevent signature malleability
- `VeChainSignature.fromBytes` rejects a high S, where the official
  SDK accepts it; such a signature would be rejected by the network
  anyway, so the SDK reports it early with a clear message
- The recovery byte is 0 or 1, as in the official SDK, not 27 or 28 as
  in Ethereum transactions
- Only 32-byte hashes can be signed or recovered; the SDK never signs a
  raw message

### Status

Phase 1 in progress: signatures and public key recovery complete and
verified against the official VeChain signature vector.   
Not ready for production use.   
Next: Mnemonic (BIP-39) (`0.0.6-dev`). 

## 0.0.4-dev

Phase 1 in progress: secp256k1 key pairs, address derivation, and the
EIP-55 address checksum.

### Added

- `VeChainKeyPair.generate`, using `Random.secure()` and discarding any
  value outside the valid range [1, n - 1]
- `VeChainKeyPair.fromPrivateKey`, validating the key length and range
- `VeChainKeyPair` getters for the private key, the 65-byte uncompressed
  public key, the 33-byte compressed public key, and the address
- `VeChainAddress.fromPublicKey` (compressed or uncompressed key),
  `VeChainAddress.parse`, and `VeChainAddress.fromBytes`
- `VeChainAddress.toString` with the EIP-55 mixed-case checksum, and
  value equality by bytes
- `VeChainCryptoException` for invalid keys and curve points, and
  `VeChainAddressException` for invalid addresses
- 67 unit tests, including the official key and address vectors from
  the VeChain SDK for JavaScript and the EIP-55 specification vectors
- Example: `example/phase1/keypair_example.dart`

### Design Decisions

- `VeChainAddress.parse` enforces EIP-55: a mixed-case address must
  match its checksum; the official SDK accepts any mixed case without
  checking it
- Short addresses are rejected instead of being padded with zeros, as
  the official `Address.of` does, because padding produces a different
  valid-looking address
- Public keys are decoded and validated explicitly: only `0x02`/`0x03`
  (33 bytes) or `0x04` (65 bytes), with the curve equation checked and
  compressed points decompressed by the SDK itself, because
  pointycastle's `decodePoint` skips the on-curve check for
  uncompressed points
- Key pair getters return copies and `toString` shows only the address;
  private key bytes cannot be reliably wiped from memory in Dart, so the
  SDK limits exposure instead of promising to erase them
- secp256k1 operations live in an internal `VeChainSecp256k1` class
  shared by keys and addresses; it is not exported

### Status

Phase 1 in progress: key pairs, address derivation and the EIP-55
checksum complete and verified against the official VeChain vectors.  
Not ready for production use.  
Next: Signatures and public key recovery (`0.0.5-dev`).

## 0.0.3-dev

Phase 1 in progress: the two hash functions VeChainThor uses, and a
strict hex codec.

### Added

- `VeChainHash.blake2b256` and `VeChainHash.keccak256`, each returning
  32 bytes
- `VeChainHash.blake2b256Concat` and `VeChainHash.keccak256Concat`,
  which hash several parts as if they were concatenated, mirroring the
  node's multi-input hash functions
- `VeChainHex.encode` (always `0x` plus lowercase digits) and
  `VeChainHex.decode` (optional `0x` prefix, any case)
- `VeChainCodecException`, thrown for invalid hex strings
- 33 unit tests, including the official BLAKE2b-256 and Keccak-256
  vectors from the VeChain SDK for JavaScript
- Example: `example/phase1/hash_example.dart`

### Design Decisions

- Keccak-256 is the legacy Keccak used by Ethereum and by the
  VeChainThor node (`NewLegacyKeccak256`), not SHA3-256; a dedicated
  test guards against mixing them up
- BLAKE2b is configured with a 32-byte digest explicitly, because the
  pointycastle default is 64 bytes
- `VeChainHex.decode` rejects an odd number of digits instead of
  padding with a leading zero as the official `Hex` type does: this
  codec handles bytes (hashes, addresses, signatures), where a missing
  digit is a copy error, not an equivalent value

### Status

Phase 1 in progress: hashing (BLAKE2b-256, Keccak-256) and the hex
codec complete and verified against the official VeChain vectors.  
Not ready for production use.  
Next: Keypair, address and checksum (`0.0.4-dev`).

## 0.0.2-dev

Phase 1 in progress: network configuration, the identity every
transaction depends on.

### Added

- `VeChainNetwork`: an immutable network definition with `name`,
  `genesisId`, `nodeUrl`, a derived `chainTag`, and a `nodeUri` getter
- Official networks as `const` values, usable as default parameters:
  `VeChainNetwork.mainnet` (chain tag `0x4a`),
  `VeChainNetwork.testnet` (`0x27`) and `VeChainNetwork.solo` (`0xf6`)
- `VeChainNetwork.custom` for private or local nodes, with validation:
  non-empty name, a genesis ID of `0x` plus 64 hex characters, and an
  absolute `http`/`https` node URL with a host
- Input normalization in `VeChainNetwork.custom`: surrounding
  whitespace is trimmed, the genesis ID is lowercased, and trailing
  slashes are removed from the node URL
- Value equality (`==` and `hashCode`) and a readable `toString` that
  shows the chain tag in hex
- `VeChainNetworkException`, thrown for any invalid network definition
- 27 unit tests covering the official constants, custom networks,
  normalization, equality, and every validation error
- Example: `example/phase1/network_example.dart`

### Design Decisions

- The chain tag is derived from the last byte of the genesis ID
  instead of being stored, so a network with an inconsistent chain tag
  cannot be built
- `nodeUrl` is a `String` rather than a `Uri`, because `Uri` cannot be
  `const`; official networks need to be `const` to work as default
  parameter values
- The solo node uses `http://127.0.0.1:8669` instead of `localhost`,
  following the official SDK, which does so to avoid IPv6 resolution
  issues
- The EVM chain ID (`0x186a9` on mainnet, `0x186aa` on testnet) is
  intentionally left out: native VeChain transactions use the chain
  tag, and the EVM chain ID will be added with the contracts phase
